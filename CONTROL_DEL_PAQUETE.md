# Control del paquete de construcción

Preparado el 22 de noviembre de 2026 para el proyecto JODA / TERRACO.

## Material incluido y verificado

- Prompt maestro con encargo de implementación, diseño, reglas y criterios de aceptación.
- Investigación inicial, matriz de 72 problemas, seis propuestas seleccionadas, base real y decisiones consolidadas.
- 99 referencias base de carta en 18 categorías. Se comprobaron nombres, descripciones, variantes y texto de precios contra la transcripción disponible.
- Precios numéricos expresados en centavos cuando permiten una transcripción; las ambigüedades se conservan como observaciones o requisitos de confirmación.
- Once recursos originales: cinco cartas, dos logos, tres capturas de referencia comercial y un video.
- Las copias de los once recursos tienen el mismo contenido binario que los originales recibidos.
- Las rutas a datos, documentos y recursos citadas en el prompt y el catálogo fueron comprobadas.

Los tres documentos de base más recientes se compararon con sus versiones actuales antes de incorporarlos. La investigación inicial se leyó completa y se conserva como antecedente fechado. La matriz contiene los 72 casos numerados, sin saltos.

## Qué significa esta revisión

Se revisó el material que recibirá Claude Code. Todavía no hay una aplicación construida dentro de este paquete, por lo que aquí no se afirma haber ejecutado pruebas de interfaz, cobros, seguridad o funcionamiento de una app.

El prompt exige que Claude construya la demo, ejecute las comprobaciones correspondientes y deje un registro de lo que pudo verificar. Los recorridos de demostración se deben revisar después con Nacho y, antes del piloto real, con el dueño, personal y DJ de TERRACO.

## Decisiones que evitan una falsa sensación de completitud

1. El estado de pago, preparación y entrega se modela por separado.
2. Todas las vistas deben compartir datos; las métricas no pueden ser gráficos de adorno.
3. La carta real se distingue de horarios, stock, mesas y promociones ficticias.
4. Un selector de rol y una persistencia local se presentan como mecanismos de demostración.
5. Las condiciones ambiguas no se convierten automáticamente en ofertas comerciales.
6. Las funciones futuras requieren servicios e infraestructura reales, además de validación operativa.

La versión de prueba está especificada para ser amplia y útil. Su calidad final depende de la implementación y de verificar que las personas puedan completar las tareas propuestas.
